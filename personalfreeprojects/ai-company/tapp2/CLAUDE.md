# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

TAPP — a garment design-to-manufacturing platform. A buyer describes/sketches a garment, AI renders it and generates a tech pack, the platform matches the design to a manufacturer, and an order is tracked through its production lifecycle. There are three actor roles: `user` (buyer/designer), `factory` (manufacturer), and `admin`.

## Repository layout — three separate git repos

This directory (`tapp2/`) is its own git repo (remote `Contribution_24mcc20001`), but `tapp-backend/` and `tapp-frontend/` are **each their own independent git repo** with their own remotes (`Prince5723/tapp-backend`, `Prince5723/tapp-frontend`). When committing or checking status, `cd` into the specific sub-repo first — running git from `tapp2/` operates on the outer repo, not the app code. A `git status` from the outer repo shows unrelated deletions from a sibling `futuretitansLastProject` folder; ignore those.

- `tapp-backend/` — Express + Mongoose REST API (port **4002**)
- `tapp-frontend/` — Next.js 15 App Router client (port **3002**)

### Required environment (backend `.env`, not committed, no `.env.example`)
`MONGODB_URI`, `JWT_SECRET`, `GEMINI_API_KEY`, `TRIPO_API_KEY`. Optional: `PORT` (default 4002), `CLIENT_ORIGIN` (comma-separated extra CORS origins — these are *added* to the baked-in localhost:3000/3001/3002 dev origins, not a replacement), `GEMINI_TEXT_MODEL` (default `gemini-flash-latest`), `GOOGLE_CLIENT_ID` (Google OAuth Web client id — enables Google sign-in). Optional AWS S3 (GLB persistence — see below): `AWS_S3_BUCKET` + `AWS_REGION` enable it; `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` (omit to use the ambient IAM role / default provider chain); `AWS_S3_PREFIX` (default `glb`). Optional credits (see below): `CREDIT_MONTHLY_ALLOWANCE` (default 300), `CREDIT_COSTS` (JSON overriding per-action prices), `STRIPE_SECRET_KEY` + `STRIPE_WEBHOOK_SECRET` (enable credit-pack purchase; absent ⇒ purchase returns 501 but the ledger/grant path still works). Frontend (`.env.local`) uses `NEXT_PUBLIC_API_URL` (default `http://localhost:4002`) and `NEXT_PUBLIC_GOOGLE_CLIENT_ID` (**must equal** the backend's `GOOGLE_CLIENT_ID`).

### GLB persistence to S3 (`utils/s3.js`)
Tripo returns the generated GLB behind a short-lived signed S3 URL *on Tripo's side*. The first `GET /api/public/model/:taskId/glb` fetches those bytes once, copies them into **our** bucket at `${AWS_S3_PREFIX}/${taskId}.glb`, and serves them; every later request for that task is served straight from our bucket (checked with a `HeadObject`), so Tripo is never hit again for the model. When S3 isn't configured (`s3Enabled()` false — no bucket/region), the route transparently falls back to proxying Tripo on every request, so local dev needs no AWS account. The response's `X-Glb-Source` header says which path served it (`s3` | `s3-cached` | `tripo`). S3 upload failures are best-effort and never fail the response.

## Architecture

### Auth and roles
JWT bearer tokens, stored client-side in `localStorage` (`tapp-frontend/src/lib/api.ts` — `api()` is the single fetch wrapper that attaches the token). Backend `middleware/auth.js` verifies the token and sets `req.userId`; `middleware/requireRole(...roles)` runs *after* `auth` to gate role-specific routes (loads the user, rejects suspended accounts). A `user` promotes itself to a factory via `POST /api/factory/me/register`, which creates a draft `Factory` and links `User.factoryId`. Frontend `components/FactoryGuard.tsx` enforces the factory-portal boundary client-side.

**Google sign-in** (`POST /api/auth/google`): Google Identity Services ID-token flow. Frontend `components/GoogleSignInButton.tsx` (used via `AuthShell`'s `SocialRow`, which takes an `intent` of `'user' | 'factory'`) obtains a Google credential and posts `{ credential, intent }`; the backend verifies it with `google-auth-library` against `GOOGLE_CLIENT_ID`. **Identity rule: one verified Google email = one `User`** — the login links onto any existing password account with the same email (`User.googleId` is set on first Google login; `passwordHash` is optional for Google-only accounts). If `intent === 'factory'` and the resolved account is a plain buyer, it is **auto-promoted** to a factory. The promote logic is shared by this route and `/me/register` via `utils/promoteToFactory.js` — change factory-shell creation there, not in either route. Google refuses non-`localhost` `http` origins and raw IP addresses, so the deployed app needs a real domain + HTTPS (register both `http://localhost:3002` and the prod origin in Google Cloud Console; the IP `159.223.85.23` will never be accepted). Full setup/deploy steps: **`GOOGLE_AUTH_SETUP.md`** at the repo root.

### Backend route map (`server.js` mounts these under `/api`)
`auth`, `design`, `factory`, `material`, `trim`, `order`, `admin`, `taxonomy`, `public/model`, `project`, `brandkit`. Each `routes/*.js` pairs with a `models/*.js` (`Design`, `Factory`, `Material`, `Order`, `Trim`, `TaxonomyTerm`, `User`, `Project`, `BrandKit`). `admin.js` applies `requireRole('admin')` to the whole router.

**`project` + `brandkit` (user-scoped, server-side stores that replaced client localStorage):** `routes/project.js` (`/api/project`) is the per-user registry of garments the buyer generated — metadata + the small dashboard thumbnail inline in Mongo, the heavy painted texture and tech-pack shots in S3 (keys on the doc), all handed back as data URLs through authed endpoints. It owns the editor's texture (`/:id/texture`), Design & Fit, and tech pack (`/:id/techpack`, `/:id/techpack-doc`). Frontend client: `src/lib/projects.ts` (async). `routes/brandKit.js` (`/api/brandkit`) is the user's reusable brand identities (name, palette, fonts, logo→S3); client `src/lib/brandKits.ts`, page `dashboard/brand-kits`. **Credit system (`routes/credits.js` + `utils/credits.js`, mounted `/api/credits`):** usage credits meter the AI/generation features (the dashboard top bar's balance). Two pools per user (`CreditAccount`): a `monthlyAllowance` that **resets each calendar month** (rollover applied lazily on read in `getAccount`) and a non-expiring `topupBalance` from Stripe purchases or admin grants; consumption draws allowance first, then top-ups, and every movement is an append-only `CreditLedger` row. `utils/credits.js` is the only place balances change — `consume`/`addCredits`/`setAllowance`, plus `chargeOrReject(req,res,action)` which routes call *after input validation, before the expensive work*: it 402s on an empty balance, no-ops for anonymous callers (`req.userId` unset), and **fails open** on infra errors so a ledger bug never blocks paid work. Per-action costs live in `BASE_COSTS` (overridable via `CREDIT_COSTS` env). Charged endpoints: `design.js` generators (generate, from-reference, render, regenerate, edit, line-art, pattern/draft, smartsegment, model/generate, part texture) and the `public/model` generators (image→3D, multiview, fabric, pattern, stamp). The `public/model` ones are no-auth, so they use `middleware/optionalAuth.js` to identify a signed-in caller — the frontend therefore sends the token (those `api()` calls dropped `auth:false`) so credits are enforced; GET polls stay anonymous. Purchase is Stripe Checkout (`POST /checkout` → hosted page; the `/webhook`, mounted with `express.raw` **before** `express.json` in `server.js`, is the idempotent source of truth that credits the buyer on `checkout.session.completed`). Admin: `POST /admin/grant`, `/admin/allowance`. Frontend: `src/lib/credits.ts`, page `dashboard/credits`, meter in `DashboardShell`.

**Base-garment catalog (Products page):** `dashboard/products` and the dashboard "Latest Products" strip are driven by `src/lib/catalog.ts` → `catalogData.json` (26 curated 3D base garments generated from `scripts/3d_models`). Each entry carries a Tripo `taskId`; its GLB lives in S3 at `glb/<taskId>.glb` and is served by the public `/api/public/model/:taskId/glb` route (no bucket-public access needed). Thumbnails are static frontend assets in `public/catalog/<slug>.png`. `ProductCard` deep-links a template into the 3D paint editor via `productEditorHref` (`/editor?taskId=…&glb=…`), where the user customizes it; saving there creates a project keyed by that taskId. To add/replace models, re-run the ingest against `scripts/3d_models` (upload GLBs to `glb/`, copy PNGs to `public/catalog/`, regenerate `catalogData.json`).

S3 key prefixes: `glb/`, `projects/<userId>/`, `brandkits/<userId>/`.

### AI pipeline (the core of the product)
- **`utils/gemini.js`** — all generative text/image work via `@google/genai`: `classifyGarment` (free-text → garment label + customization dimensions as JSON), `generateGarmentImage`/`generateGarmentImageFromReference` (front/back renders), `bakeDesignOnFabric`, `generatePatternTemplate`, `generateLineArtFlat`, `describeGarmentImage`, `generateSegmentationHint`, and the three swatch/graphic generators used by the 3D editor: `generateFabricTile` (seamless woven-material photo), `generatePatternTile` (seamless printed pattern), `generateStampImage` (a standalone centred graphic on a white background for a decal). Image generation uses `GEMINI_IMAGE_MODEL` (default `gemini-3.1-flash-image`) and goes through the shared **`generateImageWithRetry`** helper, which retries when the image model returns a text-only reply (a stochastic failure) and surfaces the real finishReason/block reason on a hard failure — reuse it for any new image generator rather than calling `generateContent` directly.
- **`utils/tripo.js`** — Tripo3D image→3D-model + semantic segmentation (v2 openapi for `image_to_model`, v3 for `/mesh/smartsegment`). Async: kick off a task, poll status. The `Design` model carries the full polling state (`tripoStatus`/`tripoTaskId`/`tripoModelUrl`… and `segStatus`/`segTaskId`/`segParts`…), each a state machine over `idle → queued → running → success | failed`.
- **`routes/publicModel.js`** (mounted at `/api/public/model`, **no auth**) — the live path that feeds the 3D paint editor. `POST /` and `/multiview` upload image(s) to Tripo and start a GLB-friendly `image_to_model`/`multiview_to_model` task (**`quad: false`** so Tripo serialises GLB, not FBX, which GLTFLoader can't read); `GET /:taskId` polls; `GET /:taskId/glb` streams the finished GLB through our origin to dodge Tripo's S3 CORS. It also hosts the editor's Gemini image endpoints: `POST /fabric`, `POST /pattern`, `POST /image` → the three generators above.
- **Two things are both called "the editor" — keep them separate.** `routes/design.js` is a **"2D-only build"**: its header comment says the Tripo/GLB/mesh pipelines were removed from *that* flow, which now runs purely off the Gemini front+back images; `utils/glb.js` (dependency-free GLB parser) and `utils/meshMeasurements.js` remain but are unused by it. The **frontend `/editor`** is a different thing — a 3D paint-on-GLB editor (next section) fed by the `public/model` Tripo path (e.g. the `dashboard/new/reference` import). So Tripo *is* live via `public/model`, just not via `routes/design.js`. Don't assume a Tripo field is wired just because a schema/util defines it — check the specific route.

### Other backend utils
`factoryMatch.js` (constraint-based factory ranking: hard requirements *exclude* a factory, soft requirements *rank* it, with explainable `reasons`/`misses`), `materialDerive.js` (derives material properties + provenance from fiber composition — used by the seed), `patternLibrary.js` + `data/patterns/*.json` (per-garment pattern templates). Generated flat images are written to `storage/flats/` (created at runtime).

### Order lifecycle
`Order` snapshots design + factory fields at creation. Status machine: `draft → submitted → declined | accepted → quoted → in_production → quality_check → ready_to_ship → shipped → delivered → completed` (plus `cancelled`, `disputed`); separate `paymentStatus` enum. An `events[]` array logs transitions. Buyers see their orders; factory owners see orders routed to their factory (authorization checked per-request in `routes/order.js`).

### Frontend
Next.js App Router under `src/app/`. Route groups by role: buyer flow (`dashboard/`, `dashboard/new/*` the guided garment-creation wizard, `editor/`, `techpack/`, `orders/`), factory flow (`factory/portal/*` with onboarding/profile/orders), and auth (`login/`, `signup/`). `@/*` aliases `src/*`. Styling is Tailwind plus hand-written CSS (`globals.css`, `auth.css`, `v2-landing.css`) using CSS custom properties (`var(--ink)`, `var(--dim)`). Shared state helpers live in `src/lib/` (`projects.ts`, `taxonomyOptions.ts`, `pendingGlb.ts`, `use-theme.tsx`).

### 3D paint editor (`src/app/editor/page.tsx` + `src/components/PaintableModel.tsx`)
The most intricate subsystem. `/editor?glb=…` loads a GLB (from the `public/model` Tripo path) and lets the user paint/texture it with `@react-three/fiber` + `drei` + `three`. Key design points — read both files together before changing any of this:

- **Two layers of "colour".** (1) A single 2048² UV **base-colour canvas** (`ctxRef`) that the brush, eraser, lasso-fill and the Color paint-bucket (`fillColorAll`) draw into — this is the garment's albedo. (2) Decals — images and text — are **separate `DecalGeometry` meshes** parented to the body mesh, not baked into the canvas.
- **Fabric & pattern are a triplanar WORLD-space overlay shader** injected via `material.onBeforeCompile` (into `<common>`, `<map_fragment>`, `<normal_fragment_maps>`, `<roughnessmap_fragment>`), deliberately UV-independent because Tripo's UV atlas has islanded/stretched seams. Two channels: **fabric** = MULTIPLY weave colour **plus relief** (bump + roughness), and **pattern** = alpha-over print. The fabric is the garment *material* and must stay under everything: its colour multiplies over painted colour (tints it, like dyeing cloth) rather than being wiped — only the pattern/print channel yields to paint via the `uCoverTex` coverage mask. Don't reintroduce a coverage term on the fabric colour.
- **Tools** flow through `toolRef` (a mutable ref of a discriminated union set by an effect, read in `PaintableModel`'s pointer handlers). Text is special: the **page** renders styled text to a canvas (`renderTextCanvas`, Google-Fonts-backed) and the model just places/updates that canvas. A placed text layer is **live-editable** — panel edits re-render it in place via `updateDecalImage`; double-click a text layer to re-open it. Decals carry `aspect` (so text keeps proportions) and `roll` (rotation handle). Size is owned by the Size slider + the selection box's resize handle, which sync to each other — the live re-render must **not** pass a new world size.
- **Rotation is universal:** non-drawing tools rotate on left-drag; drawing tools (brush/erase/lasso/add/text/fill) use left for the tool and rotate on right-drag / two-finger. Model/overlay pointer handlers ignore non-primary mouse buttons so a right-drag only orbits.
- **Undo/redo** is a full snapshot/restore in `PaintableModel` (`snapshot()` captures the base-colour ImageData, coverage mask, and every decal's full state incl. image/pose/aspect/roll; `restore()` rebuilds them). The page keeps the undo/redo stacks and calls `pushUndo()` before each mutating action.
